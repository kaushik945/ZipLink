## Infrastructure investigation and cleanup

The initial default-port Redis attempt failed with `ECONNREFUSED 127.0.0.1:6379`. Existing WSL distributions were available but had no Redis binary. The optional `scripts/build-test-redis.sh` downloaded a pinned official Redis 7.4.2 source release and compiled it under ignored `.local-services/`, without sudo or system installation. A loopback-only nonpersistent instance on port 6397 enabled all live suites.

The first live attempt exposed BullMQ 6's optional-driver requirement: queue connection options require explicit `ioredis`. That dependency is now declared, and API/worker startup waits for queue readiness. A database left by interrupting that failed attempt was identified by its exact generated test name and removed; no application database was migrated, truncated or deleted.

The temporary browser fixture used its own random test database and Redis prefix. Test service cleanup drains producer/worker, removes only its namespace and drops only that test database. The temporary Redis is shut down after verification; the existing default-port services and application `.env` are unchanged. The local nonpersistent Redis does not verify AOF crash recovery, replication or failover.

## Reproducing verification

1. Configure `.env` from `.env.example` with a random session secret and real MySQL/Redis connection values; do not replace an existing file blindly.
2. Start Redis 7+ and run `npm run test:integration -- all`. MySQL tests need CREATE/DROP DATABASE privilege for their generated names only. For optional WSL compilation, run `bash scripts/build-test-redis.sh` from the workspace in WSL. Start its binary on a dedicated loopback port and set `REDIS_URL` to that port before testing. This pinned helper is test tooling, not a production Redis installer.
3. Back up the application database before `npm run migrate`. Only isolated test databases were migrated during this task.
4. Start `npm run server`, `npm run worker`, and `npm run dev -- --port 5173 --strictPort`. Verify real HTTPS/trusted-proxy cookie behavior in the intended deployment.
5. Run the controlled fault/load procedure in `docs/BENCHMARKS.md`: stop/recover workers and Redis, measure event loss/backlog and verify recovery under load. Correctness assertions do not establish performance capacity.

## Remaining verification limits

No maximum-capacity benchmark, original synchronous baseline, HA/failover, AOF crash/restore, multi-region behavior, full Redis-server crash/recovery drill, strict immediate cache revocation, lossless pre-queue analytics, production TLS/proxy check, retention/backup job or alert pipeline is claimed. Cache invalidation is eventually consistent. Events may be lost before acceptance or on Redis data loss. Transactionally idempotent database effects are not exactly-once transport.
